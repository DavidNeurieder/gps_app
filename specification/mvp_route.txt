Absolutely. I’d make the MVP much narrower than the eventual vision, but I would build the architecture around the eventual “just go” concept.

The MVP question is:

Can we take someone's raw GPS history, automatically discover a route they've repeated, and make beating their previous performance feel compelling?

If that works, everything else becomes worth building.

MVP: "Just Go"
Core promise

Just go. We'll find the routes you repeat.

The MVP should target running and cycling, but I would initially optimize the experience for running because GPS traces are simpler and the feedback loop is frequent.

No route setup.

No account required.

No social network required.

No AI coach.

No complex training plans.

5. The hardest MVP feature: recurring route detection

Don't try to solve the entire planet.

For MVP, establish constraints.

For example:

same direction
roughly same starting location
roughly same endpoint
60–120% distance similarity
≥70% spatial overlap

Suppose the user has:

Run 1
Run 2
Run 3
Run 4


The system calculates whether they're sufficiently similar.

create a route cluster.

6. Don't use AI initially

This is important.

Map matching / nearest-path calculations.

Alignment

Conceptually:

Track A:
A A A A A A A A

Track B:
  B B B B B B B B


DTW determines correspondence despite different speeds.

Similarity

Combine:

Then produce:

8. Canonical route

Once you have several attempts, construct a canonical route.

This isn't necessarily a literal average GPS line.

Think of it as a one-dimensional coordinate system:

0m ──────────────────────────────── 7800m


Every attempt gets projected onto that axis.

Then you can compare:

Attempt A
0 → 7800m

Attempt B
0 → 7800m

Attempt C
0 → 7800m


This is the foundation of everything else.

17. Development milestones

I'd break the build into approximately six stages.

Milestone 1 — GPS engine

1–2 weeks

Build:

background tracking
GPS recording
local persistence
activity summary
map visualization

Success:

I can record a 10 km run reliably with the phone locked.

Milestone 2 — Track processing

2–3 weeks

Build:

smoothing
GPS error handling
distance calculation
elevation processing
speed/pace calculation
activity normalization

Success:

Same route recorded twice produces recognizably similar geometries.

Milestone 3 — Route discovery

3–5 weeks

Build:

activity clustering
route similarity
alignment
canonical route generation

Success:

Give the system 20–50 activities and ask:

Which activities are the same route?

You want very high precision, even if recall isn't perfect.

I'd rather fail to discover a route than incorrectly tell someone:

"These are the same."

18. Milestone 4 — Sectors

Success:

That's the validation.

22. Your first validation experiment

I'd actually do this before building the complete app.

Get GPS activity data from perhaps 20–30 runners with historical activities.

Run your Rust algorithm offline.

Ask it to discover:

Which activities belong to the same route?

Then manually label the truth.

Measure:

Route precision

Of routes the algorithm says are identical:

How many actually are?

Route recall

Of routes that are actually recurring:

How many did we discover?

I'd target something like:

>95% precision

before worrying about recall.

False route merges are devastating.

23. Then test the emotional product

Once route matching works, give ~30 people the app.

Don't explain the grand vision.

Tell them:

Just go.

After several activities, the app says:

We found a route you repeat.

Then:

Race your best.

Measure:

The key metric

Repeat-race rate

Of users who discover a route:

What percentage attempt the route again specifically to improve their time?

I'd consider:

<10% — concerning
10–25% — interesting
25–40% — promising
40%+ — extremely interesting

It's not a universal benchmark; it's the behavioral signal I'd use to judge whether you've found the game's core loop.

24. The north-star metric

I'd avoid:

Daily active users.

Too generic.

I'd use:

Competitive attempts per active user per month

An activity is just activity.

A competitive attempt is:

The user repeated a recognized route with the intention/ability to compare performance.

If users start doing:

5 → 8 → 12 → 15 competitive attempts/month

you may have something.

The one sentence MVP specification

Build a privacy-first Flutter app with a Rust local engine that passively records GPS activities, automatically identifies recurring routes, generates meaningful sectors, and lets users race their own best performance in real time — with no account or cloud required.

Do that exceptionally well before adding anything else.

If 30–50 beta users start voluntarily repeating their routes because they want to beat their ghosts, I would consider that a very strong signal to build the company.
