I found several that are much more useful for your **running/cycling route-matching engine** than generic GPS datasets.

 ## My shortlist

 ### 1\. 🥇 Run Activities — 155 real running activities

 This is probably the **best small dataset to start with**.

 Run Activities dataset on Kaggle

 It contains **155 sports activities, mainly from the Black Forest**, and importantly, the ZIP includes the **actual GPX tracks**. The dataset author says the activities were recorded with two devices having different GPS sensors, and that many runs experienced signal loss. Most tracks also share the same start/end crossroads.  Kaggle

 That's almost perfect for your use case.

 You get:

```
155 activities
      ↓
many running tracks
      ↓
different GPS devices
      ↓
GPS signal problems
      ↓
mostly common start/end area
```

 The common start/end location is particularly valuable because you can investigate whether your matcher discovers recurring routes.

 **I'd download this first.**

---

 ### 2\. 🥈 Bike Data Project — huge collection of actual cycling GPX

 Bike Data Project

 This is probably the best source for **large-scale cycling data**.

 The project currently reports more than **381,000 rides** and **6.2 million km**, and explicitly provides the openly shared contributions as a **single ZIP of GPX tracks**. The open data is licensed under ODbL.  Bike Data Project

 This is particularly useful after your basic engine works.

 I'd use it for:

```
GPX parser stress testing
        ↓
GPS filtering
        ↓
large-scale route matching
        ↓
performance benchmarking
```

 Don't download everything into your Git repository. Keep the archive outside the repo and create a small curated subset.

---

 ### 3\. 🥉 SimRa — real bicycle GPS traces from Berlin

 This one is particularly interesting because it's **real cycling behavior**, rather than planned cycling routes.

 SimRa Rides Berlin 04/24–01/25 dataset

 It contains bicycle rides recorded in the **Berlin region from April 2024 through January 2025**, including GPS traces, accelerometer traces and annotated near-miss incidents. The downloadable archive is **2.19 GB**.  DepositOnce

 This is interesting for your engine because the tracks represent actual urban cycling:

```
traffic
intersections
stops
GPS obstruction
different routes
urban GPS noise
```

 It's too large to be your first dataset, but excellent for later validation.

 **Check the included licence/terms before redistributing any files.**

---

 ## 4\. GeoLife — excellent general GPS benchmark

 GeoLife dataset information

 Although it isn't specifically a running dataset, it has **17,621 trajectories from 182 users**, about **1.2 million km**, and includes walking, cycling and other outdoor movement. About 91% of trajectories have relatively dense sampling.  Kaggle

 There's also a convenient Kaggle distribution:

 GeoLife Trajectories 1.3 on Kaggle

 The original format is PLT rather than GPX, so this is a good opportunity to make your Rust crate support **more than GPX** eventually.

 For your project I'd use GeoLife primarily for:

 - large-scale benchmarking
- noisy GPS
- different sampling rates
- repeated mobility patterns
- parser testing
- route clustering

 rather than as your primary running dataset.

---

 ## 5\. BikeZ-ETH — controlled cycling data

 This is a newer dataset and has a very different purpose.

 BikeZ-ETH dataset

 It contains high-resolution bicycle trajectory data from a **controlled mass-cycling experiment at ETH Zurich**, with 28 cyclists recorded over roughly 30 minutes under different traffic-density conditions, including free-flow, disturbed-flow and stop-and-go situations.  DOI

 This isn't what I'd use to test "does this person repeat their 7 km Sunday run?"

 But it's excellent for testing:

```
stop/start behavior
dense trajectories
cycling movement
trajectory geometry
```

 # What I would NOT prioritize

 There are lots of websites offering downloadable GPX **routes**.

 For example, Germany's official cycling network provides GPX files for its long-distance cycling routes.  Radroutenplaner Deutschland

 And EuroVelo provides GPX files for its European cycling routes under ODbL.  EuroVelo

 Those are useful for **testing your GPX parser**, but they're not particularly useful for your route-discovery algorithm.

 Why?

 Because:

```
planned route
     ≠
GPS activity
```

 Your engine needs to cope with:

```
actual person
    ↓
actual GPS
    ↓
actual deviations
    ↓
actual pauses
    ↓
actual recording errors
```

 # More importantly: create your own benchmark

 I'd turn the downloaded data into a **small labelled corpus**.

 For example:

```
testdata/
├── running/
│   ├── route_a/
│   │   ├── activity_01.gpx
│   │   ├── activity_02.gpx
│   │   ├── activity_03.gpx
│   │   └── activity_04.gpx
│   │
│   └── route_b/
│       ├── activity_01.gpx
│       ├── activity_02.gpx
│       └── activity_03.gpx
│
├── cycling/
│   ├── same_route/
│   ├── similar_route/
│   └── different_route/
│
└── synthetic/
    ├── clean.gpx
    ├── noisy_5m.gpx
    ├── noisy_10m.gpx
    ├── noisy_20m.gpx
    ├── gps_gap.gpx
    ├── stopped.gpx
    └── detour.gpx
```

 And a manifest:

```
{
  "tracks": [
    {
      "file": "running/route_a/activity_01.gpx",
      "route": "route_a",
      "expected_distance_m": 7800
    },
    {
      "file": "running/route_a/activity_02.gpx",
      "route": "route_a",
      "expected_distance_m": 7800
    }
  ]
}
```

 Then your Rust tests can say:

```
activity_01 + activity_02
        ↓
     SAME

activity_01 + activity_03
        ↓
     SAME

activity_01 + unrelated_01
        ↓
   DIFFERENT
```

 That gives you an actual **ground truth benchmark**.
