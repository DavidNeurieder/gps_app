Yes. There are a few good sources, but **I would use them for different purposes** rather than dumping one giant dataset into your project.

 ## 1\. Best starting point: Microsoft GeoLife

 Microsoft Research 's **GeoLife GPS Trajectory Dataset** is probably the best large public dataset for developing your Rust engine.

 It contains GPS trajectories from **182 users**, over several years, with **17,621 trajectories**, roughly **1.2 million km** of movement, and **48,000+ hours** of data. The points contain timestamp, latitude, longitude and altitude, and most tracks have fairly dense sampling.  Microsoft

 GeoLife official dataset page

 ### Why it's useful

 It gives you exactly the kind of ugly real-world data your engine needs:

 - different GPS devices
- different sampling intervals
- walking
- cycling
- driving
- commuting
- sightseeing
- repeated movements
- GPS noise
- long tracks

 The big downside is that it's **not primarily a running dataset**, and much of it is urban mobility. So I wouldn't use it as your only dataset.

 # 2\. OpenStreetMap public GPS traces

 This is another excellent source because you can obtain actual **GPX files** rather than having to convert some research-specific format.

 OpenStreetMap  has publicly accessible GPS traces uploaded by users. Individual trace pages expose GPX tracks with thousands of points. For example, current public traces include hiking, cycling, driving and other activities.  OpenStreetMap+1

 OpenStreetMap public GPS traces

 This is particularly nice for your project because your engine can eventually accept:

```
GPX → Track
```

 without having to invent a special test format.

 There are traces with everything from hundreds to **tens of thousands of points**, so you'll encounter realistic variation in track density.  OpenStreetMap+1

 ### Important distinction

 Don't confuse:

```
OpenStreetMap map data
```

 with:

```
OpenStreetMap GPS traces
```

 You want the **GPS traces**.

 # 3\. But there's a problem with both datasets

 For your particular engine, you need to answer:

 > **Do these two GPS tracks represent the same route?**

 A random collection of 10,000 tracks doesn't give you that ground truth.

 For example:

```
track_001.gpx
track_002.gpx
track_003.gpx
```

 might look similar, but unless you know their relationship, you can't easily say:

```
001 + 002 = SAME ROUTE
001 + 003 = DIFFERENT ROUTE
```

 That's why I'd build your test corpus differently.

 # 5\. GeoLife is particularly useful for finding repeated trajectories

 GeoLife is interesting because the data is organized by user and trajectory, rather than simply being one enormous collection of unrelated GPX files.

 You can therefore investigate:

```
User A
  ├── trajectory 001
  ├── trajectory 002
  ├── trajectory 003
  ├── ...
```

 and look for recurring movements.

 The dataset documentation specifically describes life routines such as going home and going to work, in addition to activities such as hiking and cycling.  Microsoft

 That makes it useful for experimenting with the fundamental question your app is trying to solve:

 > **Can we detect that someone repeatedly traveled the same physical course?**

 # 8\. And then make synthetic tracks

 This is something I'd strongly recommend for the Rust engine.

 Suppose you have:

```
route.gpx
```

 Your test tool can generate:

```
route_clean.gpx
route_noise_5m.gpx
route_noise_10m.gpx
route_noise_20m.gpx
route_sparse.gpx
route_dense.gpx
route_with_gap.gpx
route_with_stop.gpx
route_with_detour.gpx
route_reversed.gpx
```

 Now you have known answers:

```
                     Expected
                     --------
clean vs noise_5m     SAME
clean vs noise_10m    SAME
clean vs noise_20m    SAME
clean vs sparse       SAME
clean vs dense        SAME
clean vs stop         SAME
clean vs gap          SAME
clean vs detour       ?
clean vs reversed     DIFFERENT*
```

 `*` depending on your product decision.

 This is **far more valuable for developing the algorithm** than simply acquiring thousands of tracks.

---

 # 9\. One particularly useful trick

 Take a real GPX track and create artificial GPS errors.

 For example:

```
Real:

───────────────╮
               ╰────────────

Simulated GPS:

──────────╮  ╭─╮
          ╰──╯ ╰────────
             ↑
           noise
```

 You can then test exactly how much GPS error your matcher tolerates.

 For example:

 | Noise | Expected |
| --- | --- |
| 2 m | Same |
| 5 m | Same |
| 10 m | Same |
| 20 m | Same |
| 30 m | Probably same |
| 50 m | Depends |
| 100 m | Probably different |

 Those thresholds will ultimately come from experiments rather than guesswork.

 That gives you both **controlled correctness tests** and **real-world messiness**.
