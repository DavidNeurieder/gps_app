 # 7\. Route representation

 A route should have a stable canonical representation.

 Conceptually:

```
Route
├── id
├── geometry
├── total_distance
├── start
├── finish
└── metadata
```

 The important part is that an activity isn't compared point-for-point against another noisy GPS recording.

 Instead:

```
GPS track
    ↓
route projection
    ↓
distance along route
    ↓
time at route position
```

 That representation powers the ghost.

---

 # 8\. Route matching

 The MVP matcher should answer:

 > "Is this activity the same route as one of my existing routes?"

 It should handle:

 - GPS noise
- different sampling rates
- slightly different paths
- imperfect starts
- imperfect finishes
- running/cycling speed differences
- missing GPS points

 Return something like:

```
RouteMatch
├── route_id
├── confidence
├── matched_distance
├── coverage
└── direction
```

 Don't make the matcher return only a boolean.

 You need its confidence and diagnostic information for testing.

---

 # 9\. Route discovery

 If no existing route matches:

```
Activity
   ↓
candidate route
   ↓
canonicalize
   ↓
save as new route
```

 The user can later name it.

 The engine shouldn't depend on a human-created route beforehand.

---

 # 10\. Ghost generation

 This is central to the product.

 Given:

```
Route
+
Reference Attempt
```

 produce:

```
Ghost
```

 The ghost should allow queries like:

```
time_at_distance(1000m)
time_at_distance(2500m)
time_at_distance(5000m)
```

 Then for the current runner:

```
current_time_at_distance
-
ghost_time_at_distance
=
performance_gap
```

 This is much more robust than comparing raw GPS timestamps.

   ↓

 # 57\. The key change from the original plan

 The biggest change I'd make is that **the dataset/evaluation system becomes a first-class part of the MVP**, rather than something you do after the engine is "finished."

 The project should really be three products developed together:

```
┌──────────────────┐
│   gps-engine     │
│                  │
│ useful Rust lib  │
└────────┬─────────┘
         │
         │
┌────────▼─────────┐       ┌──────────────────┐
│   Flutter app    │◄─────►│ Evaluation/data  │
│                  │       │                  │
│ excellent UX     │       │ real GPS tracks  │
└──────────────────┘       └──────────────────┘
```

 **Rust** gives you a reusable, testable GPS/route engine.

 **Flutter** gives you the actual product experience: _you versus your previous self._

 **Real GPX data** keeps the algorithms honest and gives you a continuously growing regression suite.

 That combination gives the MVP a much stronger technical foundation than building a conventional GPS tracker first and trying to bolt the racing/route intelligence onto it later.
